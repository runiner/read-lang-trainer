# Design

## Context

Контент запечён в pkg через `include_str!` ([content_data.rs](../../crates/core/src/content_data.rs)); npm-скрипты dev/test/build уже пересобирают wasm (исправление предыдущего бага), но это соглашение, а не гарантия. CI ([deploy.yml](../../../.github/workflows/deploy.yml)) собирает pkg одним шагом, web — другим; рассинхрон сейчас ловится только глазами пользователя. См. proposal.md — зачем нужен проверяемый stamp.

## Goals / Non-Goals

**Goals:**
- Машинно проверяемое равенство «pkg ↔ content/*.json на HEAD».
- Проверка дешёвая и стоит там, где пользователь её не пропустит: CI до деплоя + локальный тест.
- Стабильный хеш: реформатирование JSON с тем же содержимым не должно обязываться менять версию… см. решение 2 — осознанное ограничение.

**Non-Goals:**
- Hot-reload контента без пересборки, HTTP-загрузка JSON в рантайме.
- Канонизация JSON (сортировка ключей и т.п.) ради «стабильности к форматированию».
- Версионирование/миграции формата документов.

## Decisions

1. **Что именно гарантируем.** Не «браузер всегда свеж» (это про кэш/HTTP — вне нашей власти), а: *любой собранный артефакт либо соответствует файлам, либо сборка падает*. Это закрывает инцидент пользователя: pkg из старого коммита невозможно выложить незамеченным.
2. **Stamp = SHA-256 конкатенации байтов двух файлов** (`levels.json` затем `stories.json`, разделитель фиксированный). Детерминированно, ~в один абзац кода. Альтернативы: канонический JSON (serde_json→sorted) — сложнее и всё равно чувствителен к whitespace внутри строк; mtime/git hash — невоспроизводимы. Следствие принятого решения: reformat файла меняет версию — это честно («байты контента изменились»), фиксируется в README.
3. **Где считается.** В core: `pub fn content_version() -> &'static str` — SHA-256 от `include_bytes!` обоих документов, вычисление const-fn или LazyLock. Зависимость: crate `sha2` (pure Rust, tiny, работает const; альтернатива `ring`/ручной вариант отвергнуты: первый тяжёл для wasm, второй — свой криптокод писать не будем). Для const-пути при недостатке const-поддержки — `LazyLock<String>`; результат тот же.
4. **Как проверяется.** Две точки, один источник истины:
   - wasm-экспорт `content_version()` → фасад `wasm.ts`; vitest-тест `freshness.test.ts`: считает SHA-256 от файлов через `node:crypto` и сверяет с pkg. Покрывает локальную работу (`npm run test`).
   - CI-шаг после build:wasm: `cargo run --example content_version`? — нет, лишнее; достаточно, что CI уже гоняет `npm run test` (pretest пересобирает pkg ⇒ тест всегда про актуальный pkg). Отдельный шаг в workflow не нужен — **упрощение**: проверка живёт в существующем тестовом шаге.
5. **Сообщение об ошибке** — обе версии (pkg vs files) в тексте assert: «пересоберите: npm --prefix web run build:wasm».
6. **README** — одна строка в разделе «Как добавить упражнение»: версия контента видна через `content_version()`, несоответствие поймает тест.

## Risks / Trade-offs

- [Чувствительность к whitespace/reformat] → принято сознательно; документ — данные, diff правки виден в git.
- [sha2 как новая runtime-зависимость core] → pure-Rust, ~безопасная поверхность, размер прироста wasm минимален; если принципиально — fallback: посчитать хеш в build.rs и включить литералом (не делаем заранее).
- [Тест проверяет pkg, а pkg может быть собран из грязной рабочей копии] → в CI checkout чистый; локально pretest пересобирает pkg перед прогоном — окно рассинхрона ≈ секунды сборки.

## Open Questions

- Показывать ли номер версии в UI (например, мелким в history) — только если понадобится поддержка «на какой версии я занимался»; здесь нет.
